# השוואת מחירים בין ספקים — מוצרים זהים בקטלוגים שונים

**נכתב:** 24.09.2026 · **סטטוס:** מאושר, לא נבנה

## למה

שאבי ודאלאס (ובעתיד ספקים נוספים) מוכרים חלק מאותם מוצרים, לעיתים במותג אחר
ובאריזה אחרת (קרטון 400 מגבונים מול חבילה של 80). מי שמזמין רואה רק את
הקטלוג של הספק שבחר, ולא יודע שאותו דבר זול יותר אצל השני.

## מה נבנה

1. **סריקת התאמות.** Claude עובר על הקטלוגים ומציע זוגות מוצרים זהים בין
   ספקים שונים, עם כמות היחידות באריזה של כל צד (כדי להשוות מחיר ליחידה
   אמיתית) והסבר קצר.
2. **מסך אישור** למנהל מערכת: "התאמות מוצרים". כל הצעה מוצגת שני מוצרים זה
   מול זה; מאשרים או דוחים; אפשר לתקן כמות באריזה. דחייה נזכרת ולא מוצעת
   שוב. אפשר גם להתאים ידנית.
3. **בטופס ההזמנה** ליד כל מוצר שיש לו התאמה מאושרת: המחיר אצל הספק האחר
   ליחידה ולאריזה, ובכמה אחוזים זול/יקר. רק התאמות מאושרות.

**לא נבנה:** החלפה אוטומטית של ספק, הזמנה מעורבת משני ספקים, השוואה בתוך
אותו ספק.

## החלטות

| שאלה | החלטה |
|---|---|
| מי מאשר | מנהל מערכת בלבד. בטופס ההזמנה מוצג רק מה שאושר |
| יחידת השוואה | "יחידת בסיס" שהבינה קובעת (מגבון, ק"ג, ליטר, יחידה, גליל…) וכמות יחידות באריזת המכירה של כל צד. מחיר ליחידה = מחיר כולל מע"מ ÷ כמות באריזה. אם הכמות לא ידועה — ההשוואה מוצגת לאריזה בלבד עם הערה "לפי אריזה" |
| מתי סורקים | אחרי כל ייבוא קטלוג (ברקע, לכל היותר פעם ב-10 דקות), ובלחיצה על "סרוק עכשיו" במסך. **לא** בעליית השרת |
| מה נסרק | רק מוצרים שטביעת האצבע שלהם (ספק+מק"ט+שם+יחידה) לא נסרקה קודם — מול כל המוצרים הפעילים של הספקים האחרים. מוצר שהשם או היחידה שלו השתנו נסרק מחדש |
| זיכרון פסקי דין | כל זוג שהוצע פעם (אושר/נדחה/ממתין) נזכר לפי שני המוצרים. זוג שנדחה לא מוצע שוב לעולם, גם אם הסריקה מציעה אותו שוב. ניסיון סריקה שנכשל לא חוזר עד הטריגר הבא |
| סף הצעה | ביטחון ≥ 0.6. מתחת — לא נשמר בכלל |
| מודל | `claude-sonnet-5`, ניתן לעקוף ב-`PRODUCT_MATCH_MODEL`. עלות נרשמת בספר ההוצאות הקיים (`aiCost`) כמו סריקת 101 |
| ספק שלישי בעתיד | קבוצה יכולה להכיל יותר משני מוצרים (אחד לכל ספק). אישור זוג שאחד מצדדיו כבר בקבוצה מאושרת — מצרף אותו לקבוצה |

## מודל הנתונים

### `ProductMatch` — קבוצת מוצרים זהים

| שדה | סוג | פירוש |
|---|---|---|
| `products` | `[{ product_id, supplier_id, pack_qty: Number\|null }]` | חבר לכל ספק. `pack_qty` = כמה יחידות בסיס באריזת המכירה |
| `base_unit` | String | מגבון / ק"ג / ליטר / יחידה… |

| `status` | `proposed` / `confirmed` / `rejected` | |

| `reason` | String | ההסבר של הבינה, מוצג במסך האישור |

## שרת

### `services/productMatch.service.js`

- `fingerprintOf(product)`.
- `runScan({ trigger })` — אוסף מוצרים חדשים (בלי סימן), ולכל ספק שולח
  ל-Claude: "אלה המוצרים החדשים של ספק X; אלה כל המוצרים של הספקים האחרים;
  החזר זוגות זהים". פלט JSON: `[{ a_id, b_id, confidence, base_unit,
  a_pack_qty, b_pack_qty, label, reason }]`. שומר `proposed` רק אם
  `confidence ≥ 0.6` ואין כבר `pair_key` כזה. מסמן את כל המוצרים שנסרקו.
  רושם שימוש בספר ההוצאות. אם אין `ANTHROPIC_API_KEY` — יוצא בשקט עם הודעה.
- `throttledScan()` — לא יותר מפעם ב-10 דקות; קריאה בזמן ריצה מתעלמת.
- `comparisonFor(supplierId)` — לכל מוצר של הספק שבקבוצה מאושרת: רשימת
  הצדדים האחרים עם `price_with_vat`, `per_unit_price` (או null), שם ספק,
  שם מוצר, יחידה, `pack_qty`, ואחוז ההפרש מול המוצר שלי.

### נתיבים (`/products/matches`, לפני `/:id`)

| נתיב | מי | מה |
|---|---|---|
| `GET /products/matches?supplier=` | תפקידי הזמנה | מאושרות בלבד, בצורת מפה `product_id → [השוואות]` |
| `GET /products/matches/review` | system_admin | `proposed` + `confirmed` עם שני המוצרים מלאים, ומועד הסריקה האחרונה |
| `POST /products/matches/scan` | system_admin | סריקה מיידית (עוקפת את ההשהיה). מחזיר כמה הוצעו |
| `POST /products/matches` `{ product_ids: [a, b] }` | system_admin | התאמה ידנית, נשמרת `confirmed` |
| `POST /products/matches/:id/confirm` `{ pack_qty: {product_id: n}, base_unit }` | system_admin | `proposed → confirmed`. אם צד כבר בקבוצה מאושרת — מיזוג |
| `POST /products/matches/:id/reject` | system_admin | `proposed → rejected` |
| `POST /products/matches/:id/unlink` | system_admin | `confirmed → rejected` (לא יוצע שוב) |

טריגר: בסוף `create` ו-`bulkImport` של מוצרים — `throttledScan()` ברקע, בלי
לחכות.

## לקוח

### מסך "התאמות מוצרים" (`/products/matches`, מנהל מערכת)

- שתי לשוניות: **ממתינות לאישור** ו**מאושרות**.
- כרטיס להצעה: שני המוצרים זה מול זה (תמונה, שם, מק"ט, יחידה, מחיר כולל
  מע"מ), שדה "כמות באריזה" לכל צד (ממולא מההצעה, ניתן לתיקון), יחידת בסיס,
  מחיר ליחידה מחושב חי, ההסבר של הבינה, כפתורים "אשר" / "לא אותו דבר".
- מאושרות: אותו כרטיס עם "בטל התאמה".
- למעלה: "סרוק עכשיו", מועד סריקה אחרונה, כמה הוצעו.
- כניסה מהניווט ליד ניהול ספקים.

### טופס הזמנה

- טוען `GET /products/matches?supplier=` פעם אחת אחרי בחירת ספק.
- מתחת למחיר של מוצר עם התאמה: שורה קטנה
  "אצל דאלאס: 0.24 ₪ ל-מגבון (97 ₪ לקרטון 400) · זול ב-12%".
  ירוק כשהספק האחר זול יותר, אפור כשהוא יקר יותר. בלי כמות באריזה:
  "אצל דאלאס: 97 ₪ לקרטון · לפי אריזה".
- אין פעולה — מידע בלבד.

## בדיקות (`server/scripts/product-match.test.js`)

1. `fingerprintOf` משתנה כששם או יחידה משתנים, ולא כשהמחיר משתנה.
2. סריקה עם Claude מדומה: הצעות מתחת ל-0.6 לא נשמרות; מעל — `proposed` עם `pair_key`.
3. אותו זוג בסריקה שנייה — לא נוצר כפול; זוג `rejected` לא חוזר ל-`proposed`.
4. מוצר שנסרק לא נשלח שוב; מוצר ששמו השתנה נשלח.
5. `throttledScan` פעמיים תוך דקה — ריצה אחת.
6. `confirm` עם צד שכבר בקבוצה מאושרת — קבוצה אחת עם שלושה חברים.
7. `comparisonFor`: מחיר ליחידה ואחוז ההפרש; `pack_qty` חסר → `per_unit_price` null.
8. `GET /products/matches` מחזיר רק מאושרות; `review` ו-`scan` נדחים למי שאינו מנהל מערכת.

## סדר בנייה מומלץ

1. מודלים + `fingerprintOf` + `runScan` עם לקוח Claude מוזרק לבדיקות + זיכרון פסקי דין. בדיקות 1–5.
2. נתיבים + `comparisonFor` + מיזוג קבוצות + טריגר אחרי ייבוא. בדיקות 6–8.
3. מסך האישור.
4. השורה בטופס ההזמנה.
5. הפעלה בפרודקשן: "סרוק עכשיו" פעם ראשונה ידנית, מעבר על ההצעות יחד.
