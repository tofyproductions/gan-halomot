# הזמנות ספקים — שמירה בהמתנה והזמנה משותפת לכמה סניפים

**נכתב:** 24.09.2026 · **סטטוס:** מאושר, לא נבנה

## למה

היום הכפתור היחיד בטופס ההזמנה הוא "שלח לאישור", והוא **שולח מייל לספק מיד**
(השם מטעה — האישור הפנימי הוא שלב נפרד שקורה אחר כך ולא שולח כלום).
אין דרך להכין הזמנה ולהשאיר אותה, ואין דרך שמנהל/ת אחר/ת ישלים/תשלים אותה.
ובגלל שכל הזמנה שייכת לסניף אחד, שני סניפים שרוצים להזמין יחד מאותו ספק —
למשל כדי לעבור את מינימום ההזמנה — לא יכולים.

## מה נבנה

שלושה דברים, כולם על מודל ההזמנה הקיים:

1. **שמירה בהמתנה.** הזמנה נשמרת כטיוטה בלי מייל. כל מי שרשאי להזמין באותו
   סניף רואה אותה ברשימה ושולח כשמתאים.
2. **הזמנה משותפת.** מתוך טיוטה מזמינים סניף נוסף. לסניף נוצרת טיוטה משלו,
   מקושרת, עם אותו ספק. כל סניף עורך רק את שלו ורואה סיכום של השאר.
3. **שליחה משותפת.** מייל אחד לספק עם קובץ הזמנה נפרד לכל סניף (כתובת, איש
   קשר למשלוח, פריטים). מינימום ההזמנה נבדק על הסכום המשותף. אחרי השליחה כל
   הזמנה ממשיכה לבד — הגעה, קליטה למלאי — כמו היום.

**לא נבנה:** שינוי בקליטה למלאי, בסטטוסים אחרי השליחה, או באישור הפנימי.
לא נבנה שיוך של הזמנה לאדם ספציפי — הסניף הוא היחידה.

## החלטות

| שאלה | החלטה |
|---|---|
| מי רואה טיוטה בהמתנה | כל בעל תפקיד הזמנה בסניף (מנהל/ת סניף, טבח/ית, מובילת כיתה, הנה"ח, מנהל מערכת) — לפי סינון הסניפים הקיים |
| מי יכול לשלוח | כל משתתף בקבוצה שרשאי להזמין. שליחה שולחת את **כל** הסניפים |
| משלוח בהזמנה משותפת | לכל סניף בנפרד. במייל: קובץ לכל סניף עם הכתובת שלו |
| סניף שהוזמן ולא הוסיף כלום | לא נשלח לספק. הטיוטה שלו מבוטלת בשליחה עם הערה "לא הוסיף פריטים" |
| מינימום הזמנה | על סכום כל הסניפים בקבוצה (לפני ביטול הריקים). בשרת ובמסך |
| הזמנה כפולה של אותו סניף לקבוצה | נדחית — סניף אחד, טיוטה אחת בקבוצה |
| התראה לסניף שהוזמן | כן — התראה בפנים + push למנהלי הסניף, דרך מערכת ההתראות הקיימת. נסגרת כשהסניף שמר פריטים או כשהקבוצה נשלחה או נמחקה |
| שם הכפתור הקיים | "שלח לאישור" → "שלח לספק" |
| תווית הסטטוס | `draft` מוצג "בהמתנה" (במקום "טיוטה") |

## מודל הנתונים

מודל `Order` מקבל שדות חדשים. אף שדה קיים לא משנה משמעות.

| שדה | סוג | פירוש |
|---|---|---|
| `group_id` | ObjectId, ברירת מחדל null | מזהה משותף לכל ההזמנות בקבוצה. null = הזמנה של סניף אחד |
| `group_invited_by` | String | שם מי שהזמין את הסניף (ריק להזמנה שיצר הסניף בעצמו) |
| `sent_at` | Date, null | מתי נשלחה לספק. הזמנות ישנות: null, ומועד היצירה הוא מועד השליחה |
| `sent_by` | String | מי לחץ "שלח" |

`status: 'draft'` כבר קיים ב-enum ובעריכה. עד היום שום דבר לא יצר אותו.

מודל `NotificationEvent` מקבל סוג חדש: `order_shared` (ref_collection `Order`).

## שרת

### נתיבים

| נתיב | מי | מה |
|---|---|---|
| `POST /orders` עם `hold: true` | canOrder | יוצר `draft`, בלי מייל. בלי `hold` — כמו היום: `pending` + מייל |
| `POST /orders/:id/send` | canOrder | טיוטה → `pending` + מייל. אם `group_id` — שולח את כל הטיוטות בקבוצה במייל אחד |
| `POST /orders/:id/invite` `{ branch_id }` | canOrder | יוצר טיוטה ריקה לסניף, קובע `group_id` על שתיהן (על המקור אם עוד אין), שולח התראה |
| `GET /orders/:id/group` | מחובר, בתחום של לפחות חבר אחד | סיכום כל החברות: סניף, מספר פריטים, סכום, סטטוס, האם שלי. **בלי פריטים** — לכן מותר לראות סניפים שאינם בתחום שלי |
| `DELETE /orders/:id` | canOrder (קיים) | מוחק טיוטה. אם היתה בקבוצה — יוצאת ממנה. סוגר את ההתראה שלה |

### שליחה — מנגנון אחד

הקוד ששולח היום מתוך `create` (מייל + רישום תוצאת המשלוח על ההזמנה) עובר
לפונקציה אחת, `dispatchOrders(orders, { supplier, user })`, שגם `create` בלי
`hold` וגם `send` קוראים לה. הזמנה אחת = קבוצה של אחת.

לקבוצה: `sendGroupOrderEmail` — מייל אחד, נמענים כמו היום (ספק, יוצר, משרד),
נושא "הזמנה משותפת: סניף א, סניף ב (#מספר)", בגוף רשימת הסניפים, ובקבצים
המצורפים קובץ ספק + קובץ פנימי **לכל סניף** (הפונקציות הקיימות
`buildSupplierHTML` / `buildInternalHTML`, פעם לכל הזמנה). תוצאת המשלוח
(`email_status`, `email_message_id`, נמענים, שגיאה) נרשמת על **כל** הזמנה
בקבוצה.

### כללי שמירה

- `send` על הזמנה שאינה `draft` → 400 "ההזמנה כבר נשלחה".
- מינימום ספק: סכום ההזמנות בקבוצה עם פריטים < `min_order_amount` → 400 עם
  הסכום החסר. הבדיקה בשרת היא הקובעת.
- `invite` לסניף שכבר בקבוצה → 400. `invite` מהזמנה שאינה `draft` → 400.
- `invite` לסניף שאינו פעיל → 400.
- שליחה מקבילה משני מנהלים: העדכון ל-`pending` נעשה ב-`updateOne` עם תנאי
  `status: 'draft'`; מי שלא תפס — מקבל 400.

### התראות

`invite` יוצר `NotificationEvent` מסוג `order_shared` לכל מנהל/ת של הסניף
המוזמן (`branchManagerFilter` הקיים), עם קישור ל-`/orders/<id>/edit`.
נסגר (`resolved`) כש: הסניף שמר פריטים (`PUT` עם פריטים), הקבוצה נשלחה, או
הטיוטה נמחקה.

## לקוח

### טופס הזמנה (`OrderForm.jsx`)

- **חדשה:** שני כפתורים. "שמור בהמתנה" (מסגרת) ו"שלח לספק" (מלא). הודעה
  אחרי שמירה: "ההזמנה נשמרה בהמתנה".
- **עריכת טיוטה:** "שמור" ו"שלח לספק". אם בקבוצה: "שלח לספק — כל הסניפים (3)".
- **לוח קבוצה** (רק אם `group_id`): מעל העגלה — שורה לכל סניף: שם, פריטים,
  סכום; "סה"כ משותף X ₪ מתוך מינימום Y ₪". הסניף שלי מודגש. נטען מ-`/group`.
- אזהרת המינימום עוברת לסכום המשותף כשיש קבוצה.

### עמוד הזמנה (`OrderView.jsx`)

- טיוטה: שבב "בהמתנה". כפתורים: "שלח לספק", "ערוך", "הזמן סניף להצטרף",
  "מחק". "הזמן סניף" פותח חלון עם רשימת הסניפים הפעילים שעדיין לא בקבוצה.
- לוח הקבוצה מוצג גם כאן, וגם אחרי השליחה (כדי לדעת עם מי הוזמן).
- הודעה בראש טיוטה שהוזמנה: "הוזמנת להצטרף על ידי <שם> מסניף <שם>".

### רשימה (`OrderList.jsx`)

- מסנן "בהמתנה". שבב קטן "משותפת · 3" ליד הסטטוס כשיש `group_id`.

### התראה

`order_shared` מופיעה בלוח ההתראות הקיים ובדחיפה; לחיצה פותחת את הטיוטה
לעריכה.

## בדיקות (בסגנון `server/scripts/*.test.js`)

`order-group.test.js`:

1. `POST /orders` עם `hold` → `draft`, `email_status` נשאר `never`, לא נקרא שולח מייל.
2. `send` על טיוטה בודדת → `pending`, מייל אחד, `sent_at` נרשם.
3. `invite` → טיוטה חדשה לסניף, `group_id` זהה על שתיהן, התראה אחת לכל מנהל/ת של הסניף.
4. `invite` פעמיים לאותו סניף → 400.
5. שליחת קבוצה: מייל **אחד**, קבצים מצורפים לפי מספר הסניפים עם פריטים, הריק מבוטל, כל חברה מקבלת `email_status`.
6. מינימום: קבוצה מתחת למינימום → 400; מעל — נשלחת גם אם כל סניף לבד מתחתיו.
7. `send` פעמיים → השני 400.
8. `GET /group` מסניף אחר בקבוצה → רואה סיכום, לא פריטים. משתמש שאינו בשום חברה → 403.
9. `PUT` עם פריטים על טיוטה שהוזמנה → ההתראה נסגרת.

בדיקות קיימות שחייבות להישאר ירוקות: `order-delivery.test.js`,
`design-hex-budget.test.js` (מספר הצבעים לא עולה — כל צבע חדש מהאסימונים).

## סדר בנייה מומלץ

1. מודל + `dispatchOrders` (חילוץ בלי שינוי התנהגות) + `hold` + `send` לבודדת. בדיקות 1, 2, 7.
2. `invite` + `group_id` + התראה + `GET /group`. בדיקות 3, 4, 8, 9.
3. מייל קבוצתי + שליחה משותפת + מינימום על הסכום. בדיקות 5, 6.
4. לקוח: טופס, עמוד, רשימה, חלון ההזמנה, לוח הקבוצה.
